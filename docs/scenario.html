۱. معرفی پروژه

در این هکاتون، شما به‌عنوان اعضای یک تیم توسعه نرم‌افزار وظیفه دارید یک پلتفرم مدیریت دارایی‌های دیجیتال را طراحی و پیاده‌سازی کنید.

هدف از توسعه این پلتفرم، فراهم کردن محیطی برای مدیریت سبد رمزارزها، مشاهده اطلاعات بازار، ثبت تراکنش‌ها، مدیریت اعضای حساب و تحلیل وضعیت دارایی‌ها است.

طراحی رابط کاربری پروژه از قبل توسط تیم طراحی آماده شده و در اختیار شرکت‌کنندگان قرار گرفته است.

مأموریت شما در تیم Backend این است که منطق تجاری، ساختار اطلاعات، امنیت و APIهای موردنیاز این رابط کاربری را پیاده‌سازی کنید.

در پایان هکاتون، انتظار می‌رود تیم شما محصولی ارائه دهد که کاربران بتوانند در آن ثبت‌نام کنند، وارد حساب خود شوند، دارایی‌هایشان را مدیریت کنند، تراکنش ثبت کنند و اطلاعات واقعی ذخیره‌شده در سیستم را در داشبورد مشاهده کنند.

محدوده پروژه

این پلتفرم یک سیستم آموزشی برای مدیریت و شبیه‌سازی دارایی‌هاست.

بنابراین موارد زیر در محدوده اجباری پروژه قرار ندارند:

  • اتصال به Blockchain
  • انتقال واقعی رمزارز
  • اتصال به حساب بانکی یا درگاه پرداخت
  • ساخت کیف پول رمزارزی واقعی
  • اجرای سفارش در صرافی
  • مدیریت کلیدهای خصوصی کاربران

تراکنش‌های خرید، فروش، واریز و برداشت، رویدادهایی شبیه‌سازی‌شده و ثبت‌شده در سیستم هستند که موجودی سبد کاربر را تغییر می‌دهند.

نکته مهم: استفاده از داده‌های نمونه برای نمایش و تست مجاز است، اما قابلیت‌های اصلی باید به دیتابیس و Business Logic واقعی متصل باشند. نمایش اطلاعات Hardcoded به‌تنهایی به معنای پیاده‌سازی قابلیت نیست.

۳. مدیریت حساب کاربران و احراز هویت

اولین بخش پروژه، طراحی و پیاده‌سازی سیستم احراز هویت کاربران است.

کاربر باید بتواند حساب کاربری ایجاد کرده و سپس وارد پلتفرم شود.

قابلیت‌های ضروری

ثبت‌نام کاربر (Register)

کاربر باید اطلاعات زیر را وارد کند:

  • نام و نام خانوادگی
  • ایمیل
  • شماره موبایل
  • رمز عبور

سیستم باید اطلاعات را اعتبارسنجی کرده و یک حساب کاربری ایجاد کند.

قوانین تجاری:

  1. ایمیل باید معتبر و غیرتکراری باشد.
  2. شماره موبایل باید دارای فرمت معتبر و غیرتکراری باشد.
  3. رمز عبور حداقل ۸ کاراکتر داشته باشد.
  4. رمز عبور نباید به‌صورت متن ساده در دیتابیس ذخیره شود.
  5. هنگام ثبت‌نام موفق، برای کاربر یک حساب سازمانی یا Workspace شخصی ایجاد شود.

ورود کاربر (Login)

کاربر باید بتواند با ایمیل یا شماره موبایل و رمز عبور وارد حساب خود شود.

پس از ورود موفق، سیستم باید اطلاعات لازم برای احراز هویت درخواست‌های بعدی را در اختیار Frontend قرار دهد.

دریافت اطلاعات کاربر جاری

Frontend باید بتواند اطلاعات کاربری را که وارد سیستم شده دریافت کند.

APIهای پیشنهادی

۴. مدیریت اشخاص و اعضای حساب

این بخش مطابق صفحه «اشخاص» در طراحی Figma پیاده‌سازی می‌شود.

هر حساب یا Workspace می‌تواند شامل چند عضو باشد. اعضا ممکن است نقش‌های متفاوتی داشته باشند.

توجه کنید که اعضای داخل پلتفرم، کاربران محصول هستند و با اعضای پنج‌نفره تیم هکاتون تفاوت دارند.

قابلیت‌های ضروری

  • مشاهده فهرست اعضا
  • جست‌وجوی اعضا بر اساس نام یا ایمیل
  • فیلتر بر اساس وضعیت
  • مشاهده نقش اعضا
  • دعوت عضو جدید
  • تغییر نقش اعضا توسط مدیر
  • فعال یا غیرفعال کردن دسترسی اعضا

سناریوی دعوت عضو

۱. مدیر، ایمیل و نقش عضو جدید را وارد می‌کند.

۲. سیستم یک دعوت‌نامه با کد یا لینک اختصاصی و تاریخ انقضا تولید می‌کند.

۳. برای نسخه اصلی پروژه ارسال ایمیل واقعی الزامی نیست؛ نمایش لینک دعوت کافی است.

۴. کاربر دعوت‌شده پس از ثبت‌نام یا ورود می‌تواند دعوت را بپذیرد.

۵. وضعیت عضو در سیستم به Active تغییر می‌کند.

هر دعوت‌نامه باید فقط یک بار قابل استفاده باشد.

قوانین تجاری

  • تنها مدیر مجاز به دعوت و تغییر نقش اعضاست.
  • کاربر نباید بدون مجوز به اطلاعات Workspace دیگر دسترسی داشته باشد.
  • یک عضو غیرفعال نباید بتواند عملیات مربوط به آن Workspace را انجام دهد.
  • حداقل یک مدیر فعال باید در Workspace باقی بماند.
  • حذف یا غیرفعال‌سازی عضو نباید تاریخچه تراکنش‌های او را از بین ببرد.

APIهای پیشنهادی

  • PATCH /api/v1/members/{id}/role

۶. مدیریت سبد دارایی

این بخش یکی از مهم‌ترین قسمت‌های پروژه است.

هر Workspace باید بتواند سبدی از رمزارزهای مختلف داشته باشد.

برای مثال، یک سبد ممکن است شامل بیت‌کوین، اتریوم، تتر و سولانا باشد.

قابلیت‌های ضروری

  • مشاهده فهرست دارایی‌های سبد
  • افزودن یک رمزارز به سبد
  • مشاهده مقدار موجودی هر رمزارز
  • نمایش قیمت فعلی
  • محاسبه ارزش کل هر دارایی
  • محاسبه ارزش کل سبد
  • محاسبه درصد سهم هر دارایی از سبد

قوانین تجاری

قانون اول ـ موجودی

برای هر رمزارز در هر Workspace یک موجودی تجمیعی نگهداری می‌شود.

مثلاً:

BTC Balance = 0.75

این موجودی باید از طریق تراکنش‌های معتبر تغییر کند، نه با تغییر دستی و مستقیم مقدار آن.

افزودن یک رمزارز جدید به سبد، در ابتدا موجودی صفر ایجاد می‌کند. برای ایجاد موجودی اولیه، کاربر باید تراکنش واریز ثبت کند.

قانون دوم ـ ارزش دارایی

ارزش دلاری هر دارایی از فرمول زیر محاسبه می‌شود:

AssetValue = Quantity × CurrentPriceUsd

مثلاً:

0.5 BTC × 60000 USD = 30000 USD

قانون سوم ـ ارزش کل سبد

ارزش کل سبد برابر مجموع ارزش همه دارایی‌های آن است.

PortfolioValue = Sum(AssetValues)

قانون چهارم ـ سهم دارایی

درصد سهم هر رمزارز از سبد:

AllocationPercentage = (AssetValue / PortfolioValue) × 100

اگر ارزش کل سبد صفر باشد، سهم دارایی‌ها نیز صفر برگردانده می‌شود.

واحد نمایش قیمت

واحد پایه محاسبات مالی پروژه دلار آمریکا است.

برای نمایش قیمت به تومان، سیستم می‌تواند از یک نرخ تبدیل آزمایشی و قابل تنظیم استفاده کند.

این نرخ باید مشخصاً آزمایشی باشد و نباید به‌عنوان نرخ واقعی بازار معرفی شود.

تیم‌ها باید مراقب باشند مبالغ دلاری و تومانی در محاسبات با یکدیگر مخلوط نشوند.

APIهای پیشنهادی

  • GET /api/v1/portfolio/holdings
  • POST /api/v1/portfolio/holdings
  • GET /api/v1/portfolio/summary
  • GET /api/v1/portfolio/allocation

۷. مدیریت تراکنش‌ها

این بخش مهم‌ترین قسمت Business Logic پروژه محسوب می‌شود.

کاربران باید بتوانند عملیات مالی شبیه‌سازی‌شده را ثبت کنند و تاریخچه این عملیات را مشاهده کنند.

قوانین تجاری

قانون اول ـ اعتبار مقدار

مقدار تراکنش باید بزرگ‌تر از صفر باشد.

قانون دوم ـ موجودی کافی

برای عملیات Withdrawal، Sell و Transfer باید موجودی کافی وجود داشته باشد.

مثلاً اگر موجودی کاربر ۰٫۵ بیت‌کوین باشد، امکان برداشت ۰٫۸ بیت‌کوین وجود ندارد.

قانون سوم ـ تغییر موجودی

هر تراکنش موفق باید موجودی متناظر را اصلاح کند.

مثال:

موجودی اولیه:

BTC = 1.5

ثبت تراکنش فروش:

Sell = 0.4 BTC

موجودی نهایی:

BTC = 1.1

قانون چهارم ـ یکپارچگی اطلاعات

ثبت تراکنش و تغییر موجودی باید یک عملیات یکپارچه باشند.

نباید شرایطی ایجاد شود که تراکنش ثبت شده باشد، اما موجودی تغییر نکرده باشد یا برعکس.

قانون پنجم ـ ثبت قیمت

برای خرید و فروش، قیمت واحد در زمان ثبت عملیات ذخیره شود تا با تغییر قیمت بازار، اطلاعات تاریخی تراکنش تغییر نکند.

قانون ششم ـ عدم تغییر تاریخچه

تراکنش موفق نباید به‌صورت مستقیم حذف یا ویرایش شود.

در صورت نیاز به اصلاح اطلاعات، باید عملیات اصلاحی مستقل ثبت شود.

وضعیت تراکنش‌ها

وضعیت‌های مورد پشتیبانی در مدل داده:

  • Pending
  • Completed
  • Rejected

در نسخه اصلی، تراکنش‌های معتبر می‌توانند مستقیماً Completed شوند.

پیاده‌سازی فرآیند تأیید یا رد تراکنش‌های Pending، قابلیت پیشرفته محسوب می‌شود. در این حالت، موجودی فقط در زمان تأیید نهایی تغییر می‌کند و رد تراکنش نباید اثری بر موجودی داشته باشد.

APIهای پیشنهادی

  • GET /api/v1/transactions/{id}
  • POST /api/v1/transactions

۱۵. Clean Architecture ـ ۷ امتیاز

تیم‌هایی که پروژه را بر اساس اصول Clean Architecture پیاده‌سازی کنند، می‌توانند امتیاز ویژه دریافت کنند.

ساختار پیشنهادی:

  • Domain
  • Application
  • Infrastructure
  • Presentation / API

معیارهای ارزیابی

  • رعایت Dependency Rule
  • مستقل بودن Domain از Infrastructure
  • جداسازی Business Logic از Controller
  • استفاده صحیح از Dependency Injection
  • مشخص بودن مسئولیت کلاس‌ها و سرویس‌ها
  • پرهیز از وابستگی مستقیم Application به EF Core یا Controller

نکته: صرفاً ایجاد چهار پروژه با نام‌های بالا به معنی پیاده‌سازی Clean Architecture نیست.

تیم باید بتواند توضیح دهد چرا هر بخش در لایه مربوط به خودش قرار گرفته است.

۱۶. CQRS ـ ۶ امتیاز

تیم‌ها می‌توانند عملیات خواندن و نوشتن را بر اساس الگوی CQRS از یکدیگر جدا کنند.

برای مثال:

Queryها:

  • GetPortfolioSummaryQuery
  • GetTransactionsQuery
  • GetMarketAssetsQuery

Commandها:

  • CreateTransactionCommand
  • AddHoldingCommand
  • InviteMemberCommand

معیارهای ارزیابی

  • جداسازی منطقی Command و Query
  • مسئولیت مشخص Handlerها
  • عدم قرارگیری Business Logic در Controller
  • امکان تست مستقل عملیات
  • استفاده صحیح از DTO و مدل‌های ورودی و خروجی

استفاده از MediatR یا کتابخانه مشابه مجاز است، اما الزامی نیست.

هدف، درک و پیاده‌سازی CQRS است؛ نه صرفاً اضافه کردن یک کتابخانه به پروژه.

استفاده از دیتابیس جداگانه برای Read و Write الزامی نیست.

۱۷. Automated Testing ـ ۵ امتیاز

تیم‌ها می‌توانند برای قوانین مهم تجاری تست خودکار بنویسند.

سناریوهای پیشنهادی:

  • ثبت‌نام با ایمیل تکراری رد شود.
  • کاربر بدون مجوز نتواند عضو جدید دعوت کند.
  • برداشت بیشتر از موجودی رد شود.
  • تراکنش موفق موجودی را به‌درستی تغییر دهد.
  • موجودی هیچ‌وقت منفی نشود.
  • کاربر نتواند تراکنش Workspace دیگر را مشاهده کند.
  • ارزش سبد به‌درستی محاسبه شود.
  • ثبت تراکنش ناموفق موجودی را تغییر ندهد.

استفاده از xUnit، NUnit یا MSTest قابل قبول است.

تست‌ها باید رفتار واقعی سیستم را بررسی کنند و صرفاً برای افزایش تعداد تست نوشته نشده باشند.

۱۸. اتصال به اطلاعات واقعی بازار ـ ۴ امتیاز

تیم‌هایی که از داده‌های واقعی بازار استفاده کنند، امتیاز بیشتری دریافت می‌کنند.

موارد قابل ارزیابی:

  • استفاده از HttpClient به‌شکل صحیح
  • ذخیره قیمت‌های دریافت‌شده
  • به‌روزرسانی دوره‌ای با BackgroundService
  • مدیریت Timeout و خطاهای سرویس خارجی
  • استفاده از آخرین قیمت ذخیره‌شده هنگام قطعی سرویس
  • استفاده مناسب از Cache برای کاهش درخواست‌های تکراری

Redis اختیاری است و استفاده صحیح از آن می‌تواند در ارزیابی این بخش مؤثر باشد.

۱۹. Concurrency و Idempotency ـ ۳ امتیاز

تیم‌هایی که از اجرای تکراری عملیات مالی و بروز ناسازگاری در درخواست‌های هم‌زمان جلوگیری کنند، امتیاز ویژه دریافت می‌کنند.

مثلاً:

اگر کاربر دو بار به‌صورت هم‌زمان درخواست برداشت ۰٫۸ بیت‌کوین ارسال کند، اما موجودی او فقط ۱ بیت‌کوین باشد، سیستم نباید هر دو برداشت را با موفقیت انجام دهد.

همچنین ارسال مجدد همان درخواست به علت مشکل شبکه نباید به ثبت تراکنش تکراری منجر شود.

استفاده صحیح از Concurrency Token، Constraint و Idempotency Key از راهکارهای قابل قبول است.

۲۰. Docker و CI ـ ۳ امتیاز

معیارهای این بخش:

  • امکان اجرای پروژه در Docker
  • آماده‌سازی دیتابیس برای محیط اجرا
  • اجرای Build و Test با GitHub Actions یا ابزار مشابه
  • مستندسازی نحوه اجرای پروژه

۲۱. امنیت پیشرفته ـ ۲ امتیاز

پیاده‌سازی واقعی یکی از قابلیت‌های زیر می‌تواند امتیاز ویژه داشته باشد:

  • احراز هویت دومرحله‌ای با TOTP
  • گردش امن Refresh Token
  • فرآیند تأیید و رد برداشت‌ها با کنترل دسترسی

قابلیت انتخاب‌شده باید قابل تست باشد و صرفاً در ظاهر برنامه نمایش داده نشود.

۲۲. همکاری Backend و Frontend

یکی از اهداف اصلی این هکاتون، تجربه همکاری در یک تیم نرم‌افزاری است.

بنابراین انتظار می‌رود اعضای Backend و Frontend از روزهای ابتدایی درباره موارد زیر به توافق برسند:

  • آدرس APIها
  • مدل درخواست‌ها و پاسخ‌ها
  • ساختار خطاها
  • روش احراز هویت
  • نحوه Pagination و Filtering
  • نام فیلدها و Enumها
  • نحوه ارسال و نمایش مقادیر مالی
  • نحوه مدیریت Loading، Empty State و Error State

تیم Backend نباید تمام APIها را در انتهای پروژه در اختیار Frontend قرار دهد.

بهتر است هر قابلیت پس از تکمیل، در اختیار توسعه‌دهندگان Frontend قرار بگیرد.

همکاری با Git

  • استفاده از Repository مشترک
  • توسعه قابلیت‌ها در Branchهای مستقل
  • ثبت Pull Request
  • بررسی تغییرات یکدیگر
  • جلوگیری از Commit مستقیم تغییرات ناپایدار به Branch اصلی
