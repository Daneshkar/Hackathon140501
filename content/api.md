# قرارداد API نسخه ۱

این قرارداد، جزئیات تکمیلی پیشنهادی برای اجرای سناریوی ارسالی برگزارکننده است. متن کامل سناریو در صفحه سناریو حفظ شده است. تغییر قرارداد باید با Frontend توافق و در PR مستند شود. فایل ماشین‌خوان OpenAPI کنار همین صفحه قابل دریافت است. این ریپوزیتوری مرجع آموزشی است و Backend اجرایی ارائه نمی‌کند.

## قرارداد مشترک

- پیشوند همه مسیرها: `/api/v1`؛ JSON با نام‌گذاری camelCase و Enum رشته‌ای و حساس به بزرگی حروف.
- تمام مسیرها به‌جز register و login خصوصی هستند. تاریخ و زمان ISO 8601 به UTC است.
- مسیرهای Workspace با هدر `X-Workspace-Id` انتخاب می‌شوند؛ Backend باید عضویت فعال و نقش را از دیتابیس بررسی کند. این هدر به‌تنهایی مجوز نیست.
- `/auth/me`، `/settings` و `/watchlist` متعلق به کاربر جاری‌اند؛ هدر Workspace لازم ندارند. markets برای هر کاربر احرازشده قابل خواندن است.
- شناسه‌ها UUID؛ symbol با حروف بزرگ؛ ایمیل trim و lowercase و شماره موبایل پس از نرمال‌سازی به E.164 یکتا است.
- مقدار و پول به شکل رشته decimal ارسال و دریافت شوند؛ quantity تا ۸ رقم اعشار و price تا ۸ رقم اعشار. از محاسبه مالی با float پرهیز کنید. ذخیره quantity و price با decimal(28,8)، ارزش حاصل با precision مناسب و خروجی حداکثر ۱۶ رقم اعشار؛ ورودی فراتر از precision را با 400 رد کنید، بی‌صدا گرد نکنید.
- واحد پایه USD است. TOMAN صرفاً با نرخ آزمایشی مشخص و قابل تنظیم در لایه نمایش استفاده می‌شود.
- فهرست‌ها: page از ۱، pageSize پیش‌فرض ۲۰ و حداکثر ۱۰۰؛ پاسخ `{items, page, pageSize, totalCount}`. پارامتر نامعتبر 400؛ صفحه خارج از محدوده items خالی دارد. ترتیب پیش‌فرض createdAt نزولی و سپس id برای رفع تساوی؛ تاریخچه قیمت صعودی.
- خطا: `{code, message, traceId, errors}`؛ errors نگاشت نام فیلد به آرایه پیام‌هاست. هیچ stack trace یا PasswordHash یا token در log و خطا برنگردد.

## احراز هویت و دعوت

Register نام، ایمیل، موبایل و password حداقل ۸ کاراکتر دریافت می‌کند؛ ایجاد User و Workspace و Admin باید یکپارچه باشد. خروجی 201 شامل user و workspaceId است. Login با identifier ایمیل یا موبایل و password، خروجی 200 با accessToken و expiresIn و tokenType برابر Bearer دارد. شکست ورود پیام عمومی با 401 دارد. /auth/me کاربر و عضویت‌های فعال را برمی‌گرداند. سیاست عمر پیشنهادی access token برابر ۳۶۰۰ ثانیه است؛ refresh token جزو پایه نیست.

دعوت تنها برای Admin، دارای role غیر Admin یا Admin و عمر پیشنهادی ۴۸ ساعت است. پاسخ 201 شامل token و expiresAt است تا لینک آزمایشی ساخته شود؛ ارسال ایمیل واقعی لازم نیست. توکن تصادفی امن و فقط hash آن ذخیره شود. پذیرش دعوت با هویت احرازشده و ایمیل مطابق دعوت، یک‌بار و اتمیک انجام می‌شود؛ منقضی یا مصرف‌شده 409، ایمیل نامنطبق 403. پذیرش به Workspace دعوت مربوط است و هدر انتخاب Workspace نمی‌خواهد. عضو موجود دوباره اضافه نمی‌شود.

## ماتریس دسترسی

| عملیات | Admin | Accountant | Analyst | Member |
|---|---|---|---|---|
| خواندن سبد، داشبورد و تراکنش | بله | بله | بله | بله |
| افزودن Holding و ثبت تراکنش | بله | بله | خیر | خیر |
| فهرست و مدیریت اعضا و دعوت | بله | خیر | خیر | خیر |
| بازار و Watchlist و تنظیمات شخصی | بله | بله | بله | بله |

این ماتریس تفسیر اجرایی نقش‌های پیشنهادی سناریو است. عضو غیرفعال در Workspace به هیچ مسیر خصوصی آن دسترسی ندارد. تغییر نقش یا غیرفعال‌سازی آخرین Admin فعال 409 است؛ حتی در درخواست‌های هم‌زمان. منبع متعلق به Workspace دیگر با 404 پنهان شود؛ کاربر احرازشده فاقد نقش مناسب 403 می‌گیرد.

## تراکنش و محاسبات

- body تراکنش: assetId، type، quantity، unitPriceUsd برای Buy و Sell الزامی و مثبت؛ description اختیاری تا ۵۰۰ کاراکتر. workspaceId و createdBy و status از body پذیرفته نشوند.
- Deposit و Buy موجودی را زیاد؛ Withdrawal و Sell و Transfer موجودی را کم می‌کنند. Transfer فقط خروجی شبیه‌سازی‌شده است و برای مقصد موجودی ایجاد نمی‌کند.
- در پایه، موفقیت 201 با Completed؛ مقدار نامعتبر 400 و موجودی ناکافی 409 با `INSUFFICIENT_BALANCE`. خطا هیچ تغییری در Holding و Transaction ایجاد نکند.
- Holding باید قبلاً با موجودی صفر ایجاد شده باشد؛ تکرار ایجاد Holding برابر 409. ثبت تراکنش برای Holding ناموجود برابر 404 است.
- Buy و Sell قیمت ثبت‌شده ورودی را نگه می‌دارند. برای انواع دیگر unitPriceUsd ارسال نشود و خروجی unitPriceUsd و totalValueUsd برابر null است. ارزش کل خرید و فروش quantity ضرب‌در قیمت ثبت‌شده است.
- Pending و Rejected در schema موجودند، اما کلاینت وضعیت را تعیین نمی‌کند. فرآیند تأیید اختیاری باید endpoint مستقل و کنترل نقش و تغییر وضعیت اتمیک داشته باشد و قرارداد خود را مستند کند.
- تاریخچه موفق immutable است؛ endpoint حذف و ویرایش ندارد. اصلاح اختیاری با رویداد مستقل دارای reference انجام می‌شود.
- ارزش سبد مجموع quantity ضرب‌در آخرین قیمت ذخیره‌شده است. allocation در سبد صفر، صفر است. اگر برای دارایی قیمت موجود نیست، مجموع و allocation برابر null و pricingComplete برابر false، نه ارزش صفر جعلی.
- PnL24h از موجودی فعلی ضرب‌در اختلاف قیمت فعلی و قیمت مرجع ۲۴ ساعت قبل محاسبه می‌شود؛ سود تحقق‌یافته نیست. مرجع آخرین snapshot در یا قبل از زمان هدف است. نبود مرجع در هر دارایی غیرصفر، pnl24hUsd برابر null می‌دهد.
- portfolio-history فقط snapshotهای واقعی همان Workspace را برمی‌گرداند؛ کاربر تازه items خالی می‌بیند. seed تاریخی تنها برای Workspace آزمایشی برچسب‌خورده مجاز است.

## فیلترها و خطاها

members: search و status. markets: search و sort برابر priceAsc، priceDesc، changeAsc یا changeDesc. transactions: type، status، assetId، from و to؛ بازه شامل دو مرز و from کوچک‌تر یا مساوی to. history: from و to با ترتیب صعودی. recent-transactions: صفحه‌بندی مانند فهرست تراکنش‌ها.

200 خواندن و ویرایش؛ 201 ایجاد؛ 204 افزودن یا حذف idempotent در Watchlist؛ 400 اعتبارسنجی؛ 401 توکن غایب یا منقضی؛ 403 نقش ناکافی؛ 404 منبع ناموجود یا متعلق به Workspace دیگر؛ 409 تعارض؛ 429 محدودیت درخواست همراه Retry-After؛ 500 خطای غیرمنتظره با traceId.

## امتیاز ویژه Idempotency

هدر اختیاری `Idempotency-Key` در POST transactions با scope کاربر و Workspace ذخیره شود. کلید و payload یکسان، همان نتیجه و شناسه را برگرداند؛ کلید یکسان و payload متفاوت 409. ذخیره نتیجه و تغییر موجودی باید یکپارچه باشد. سیاست پیشنهادی نگهداری کلید حداقل ۲۴ ساعت است. تیمی که این قابلیت را ندارد، نباید ادعای اجرای آن را داشته باشد.

## نمونه مسیر اصلی

1. Register سپس Login؛ accessToken را از پاسخ بخوانید.
2. GET /auth/me و انتخاب workspaceId از عضویت فعال.
3. GET /markets/assets و انتخاب assetId.
4. POST /portfolio/holdings با `{ "assetId": "UUID" }` و هدر Workspace.
5. POST /transactions با `{ "assetId": "UUID", "type": "Deposit", "quantity": "1.5" }`.
6. POST /transactions با Sell و quantity برابر "0.4" و unitPriceUsd برابر "60000"؛ موجودی نهایی "1.1".
7. برداشت "2" باید 409 بدهد و موجودی "1.1" باقی بماند.
